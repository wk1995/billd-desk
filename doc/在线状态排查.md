# 设备一直显示「不在线」排查说明

> 最后更新：2026-10-29
> 相关分支：`local-mac-backend`
> 后端：`http://100.70.34.72:4300`（Mac + Tailscale）

## 一、先看结论

主控端提示「该设备不在线」**不代表网络不通**，它只取决于一个接口：

```
GET /desk_user/find_receiver_by_uuid?uuid=<设备代码>
→ {"code":200,"data":{"receiver":""}}      // 不在线
→ {"code":200,"data":{"receiver":"<socketId>"}}  // 在线
```

`receiver` 有值的前提是：**被控端客户端**连上 socket.io 后，成功发送 `billdDeskJoin`，
并且服务端把它的 socket 登记到 `deskUserUuid` 下。

所以排查顺序永远是：**被控端设备信息 → socket 连接 → join 是否带上设备代码 → 服务端是否登记**，
而不是先去查网络。

## 二、完整链路

```
remote 页面 mount
  └─ initDeskUser()            有缓存则 /desk_user/login，无缓存则 /desk_user/create
       └─ roomId = cacheStore.deskUserUuid
  └─ initWs({ roomId })        new WebSocketClass → io(ws://100.70.34.72:4300)
       └─ socket 'connect'
            └─ sendJoin()      emit billdDeskJoin { deskUserUuid, deskUserPassword, live_room_id }
                 └─ 服务端回 billdDeskJoined
                      └─ 服务端把 socket 登记到 deskUserUuid → find_receiver_by_uuid 才有值
```

主控端点击「连接」时只做一件事：调 `find_receiver_by_uuid`，返回空就提示不在线。

## 三、2026-10-29 已定位并修复的问题

**问题**：`src/views/remote/index.vue` 里 `const { initWs, connectStatus } = useWebsocket();`
只解构了两个返回值，**从未把 `cacheStore.deskUserUuid / cacheStore.deskUserPassword`
回填给 `useWebsocket()` 内部的同名 ref**。

于是 `use-websocket.ts` 的 `sendJoin()` 发出的是：

```js
{ deskUserUuid: '', deskUserPassword: '', live_room_id: 'Ruh9M46L' }
```

服务端照样回 `billdDeskJoined`（所以界面完全不报错），但不会把 socket 登记到该设备代码下，
`find_receiver_by_uuid` 永远返回空 → 一直显示「该设备不在线」。

**实测对照**（node + socket.io-client 模拟 join，2.5s 后查询）：

| join 内容 | 是否收到 joined | find_receiver_by_uuid |
| --- | --- | --- |
| `deskUserUuid` + 正确密码 + `live_room_id` | 是 | 返回 socketId ✅ |
| `deskUserUuid: ''` + `deskUserPassword: ''` + 正确 `live_room_id` | 是 | 返回空 ❌ |

**已修复**：`src/hooks/use-websocket.ts` 的 `sendJoin()` 改为
`deskUserUuid.value || cacheStore.deskUserUuid`，密码同理；uuid 仍为空时打日志并放弃本次 join。

> `webrtc` 页面因为从 `route.query` 赋了值，所以那条路径一直是正常的，问题只在 `remote` 页面。

## 四、本次新增的诊断能力

### 1. 统一日志前缀 `[desk-debug]`

控制台过滤 `desk-debug` 即可看到整条链路，每一步都带上下文。

| 日志 step | 含义 | 关键字段 |
| --- | --- | --- |
| `initDeskUser 开始` | 开始准备设备信息 | `mode`（create/login）、脱敏后的 uuid/密码 |
| `create 设备结果` / `login 设备结果` | 接口返回 | `code`、`message` |
| `initDeskUser 完成` | 设备信息是否就绪 | `roomId`、`state`、`hint` |
| `initDeskUser 异常` | login 校验失败（400 会走 catch） | `error` |
| `initWs 开始连接` | 开始建 socket | `roomId`、`url` |
| `initWs 警告：roomId 为空` | 设备信息没准备好 | 脱敏后的 uuid/密码 |
| `socket 已连接，准备 join` | ws 已通 | `socketId`、`url` |
| `发送 billdDeskJoin` | join 已发出 | 脱敏信息、`liveRoomId`、`uuidFrom`、`socketId` |
| `sendJoin 跳过 / sendJoin 失败` | join 没发出去 | 失败原因、`wsMapKeys` |
| `服务端已确认 joined` | 服务端已回执 | `liveRoomId`、`receiver` |
| `socket 已断开` / `socket 连接失败，正在重试` | 连接异常 | `url`、`reason`/`message` |
| `查询设备是否在线（find_receiver_by_uuid）` | 主控端查询结果 | `uuid`、`code`、`receiver` |
| `设备不在线：服务端没有该设备代码对应的 socket 登记` | 查询为空 | `uuid`、`selfUuid`、`hint` |

密码只输出「已设置(长度N)」或「(空)」，不会把临时密码写进日志。

### 2. 状态机 `DeskJoinStateEnum`

定义在 `src/types/websocket.ts`，由 `useWebsocket()` 暴露为 `deskJoinState`：

```
idle → preparingUser → userReady → wsConnecting → wsConnected → joinSent → joined
                └→ prepareUserFailed              └→ joinFailed
                                                  └→ wsDisconnected（重连后回到 wsConnected）
```

| 状态 | 含义 | 说明 |
| --- | --- | --- |
| `idle` | 未开始 | 页面刚加载 |
| `preparing-user` | 正在 create/login | — |
| `prepare-user-failed` | 设备信息不可用 | login 失败或 uuid 为空，**根本原因通常在这一步** |
| `user-ready` | 设备信息就绪 | `roomId` 已有值 |
| `ws-connecting` | socket 连接中 | 连不上时状态会反复停留在这里 |
| `ws-connected` | socket 已通 | 紧接着会 sendJoin |
| `join-sent` | join 已发出 | 等 `billdDeskJoined` |
| `joined` | 服务端已确认 | **此时主控端必须能查到 receiver** |
| `join-failed` | join 没发出去 | socket 实例缺失或 uuid 为空 |
| `ws-disconnected` | 连接断开 | 服务端会认为设备下线 |

在 remote 页面连点 5 次开启 debug 面板（`appStore.showDebug`），可直接看到
`join状态` / `ws状态` / `roomId` / `socketId`。

## 六、如果状态到 joined 但依然查不到

说明客户端已经按协议发对了，问题在服务端 `billdDeskJoin` 的处理：

- 服务端是否用 `deskUserUuid` 作为登记 key（而不是 `live_room_id`）；
- 是否在 `socket.on('disconnect')` 时正确地删除登记；
- 是否存在多进程/集群导致登记在 A 进程、查询打到 B 进程（内存 Map 不共享）；
- 服务端是否对 `deskUserPassword` 做了额外校验并静默失败。

建议服务端在 `billdDeskJoin` 成功登记后补一条日志：
`join ok uuid=<deskUserUuid> socket=<socket.id> room=<live_room_id>`，
以及在 `find_receiver_by_uuid` 返回空时打印查询的 key，便于两侧对齐。

## 七、常见误判：设备代码会变

设备代码（`deskUserUuid`）不是固定的，下列情况会重新 `create` 一个新代码：

- 点击「此设备」旁的刷新按钮（`handleResetDeskuuid` 会清空缓存后重新 create）；
- localStorage 丢失（清缓存、重装、换构建产物）；
- dev 模式下 Vite 端口变化（`localhost:5173` 与 `5174` 属于不同 origin，localStorage 不互通）。

判断方法：被控端界面「此设备」显示什么，就用什么。历史上用过的旧代码在服务端仍然存在
（`login`/`join` 都能通过），但永远不会有 socket 在线，查到的一定是空。

## 八、附：手动模拟 join 的排查脚本

```js
// node test/check-join.mjs <uuid> <password> [empty]
// empty 模式会模拟「前端发空 deskUserUuid」的历史 bug
import { io } from 'socket.io-client';

const BASE = 'http://100.70.34.72:4300';
const [TARGET, PWD, MODE] = process.argv.slice(2);
const socket = io(BASE, { transports: ['websocket'] });

socket.on('connect', () => {
  const data = MODE === 'empty'
    ? { deskUserUuid: '', deskUserPassword: '', live_room_id: TARGET }
    : { deskUserUuid: TARGET, deskUserPassword: PWD, live_room_id: TARGET };
  socket.emit('billdDeskJoin', {
    request_id: 'check123',
    socket_id: socket.id,
    user_info: {},
    user_token: '',
    time: Date.now(),
    data,
  });
});

socket.onAny((event, ...args) => console.log('[recv]', event, args));

setTimeout(async () => {
  const res = await fetch(`${BASE}/desk_user/find_receiver_by_uuid?uuid=${TARGET}`);
  console.log('[find_receiver_by_uuid]', await res.text());
  socket.close();
  process.exit(0);
}, 2500);
```

## 十、Windows 侧白屏定位结果（2026-10-29 08:14）

### 根因：加载了远程 CDN 上的旧 JS

`dist/index.html` 在本轮修复前引用的是：

```
https://resource.hsslive.cn/billd-desk/dist/assets/index-*.js
```

原因在构建脚本：`npm run build:prod` 强制 `VITE_APP_RELEASE_PROJECT_ISWEB=true`，
而 `vite.config.ts` 的 `outputStaticUrl()` 在 `isWeb && isProduction` 时返回 CDN 前缀，
于是 `base` 和 `PUBLIC_PATH` 都变成 CDN 地址。Electron 用 `loadFile` 打开本地
`index.html`，实际执行的却是 CDN 上的旧构建，`src` 与本地代码不一致 → 远控页白屏。

`npm run build:prod -- --base=./` 只能修好 `index.html` 的 script 地址，
`PUBLIC_PATH` 仍然是 CDN（产物里能 grep 到 `resource.hsslive.cn`），并未彻底解决。

### 修复：新增本地构建脚本 `build:local`

`package.json` 新增：

```bash
npm run build:local     # = cross-env VITE_APP_RELEASE_PROJECT_ISWEB=false vite build
```

`isWeb=false` 时 `base` 与 `PUBLIC_PATH` 同时为 `./`，产物内不再出现任何远程域名。
校验命令（应无输出）：

```bash
grep -c "resource.hsslive.cn" dist/index.html dist/assets/*.js | grep -v ":0"
grep -o 'PUBLIC_PATH:"[^"]*"' dist/assets/*.js   # 期望 PUBLIC_PATH:"./"
```

**本地运行（Windows / Mac 调试）一律用 `npm run build:local`，不要用 `build:prod`**，
后者是给 Web 部署用的。`.workbuddy/skills/run-billd-desk-dev/scripts/build.cmd`
等价于前者。

另外，从 Git Bash 直接拉起 Electron 时必须清掉宿主环境变量，否则主进程会报
`Cannot read properties of undefined (reading 'isPackaged')`：

```bash
env -u ELECTRON_RUN_AS_NODE -u NODE_OPTIONS electron.exe <repo> --no-sandbox
```

## 十一、画面模糊的原因与「自适应」（2026-10-29 08:4x）

Windows 端实测：主控窗口 2473×1391，但收到的视频只有 **1440×810**，被 CSS 拉满窗口，
等于放大了 1.7 倍，所以糊。追下来有三个原因，叠加在一起：

1. **被控端根本没设置码率**：`src/hooks/webrtc/remoteDesk.ts` 的 `newWebRtc` 里
   `maxBitrate / maxFramerate / resolutionRatio` 三行是注释掉的，被控端一直用浏览器默认码率。
   码率不够时编码器会主动降分辨率，`2560×1440` 的源被压成 `1440×810`。
2. **首帧参数用的是旧值**：被控端收到 `billdDeskStartRemoteResult` 后先 `appStore.remoteDesk.set(...)`
   再立刻 `handleRTC()`，而参数同步靠 `watch(appStore.remoteDesk)`，watch 是异步的，
   建连时用的还是默认的 `2000kbps / 1080`。
3. **显示端强制放大**：`videoFullBox()` 里 `computeBox` 的 `minHeight/maxHeight` 都传了窗口尺寸，
   视频不论分辨率多少都会被拉到铺满窗口，天然放大。

### 已做的修复

- `useRTCParams` 的分辨率选项新增 `自适应`（value `0`，放在末尾避免影响已有下标引用），
  码率选项补回 `6000 / 8000`
- `utils` 新增 `resolveResolutionRatio()`：按**屏幕可用高度 × devicePixelRatio** 匹配档位
  （不能按窗口算，remote 页面是 800×500 的小窗）；新增 `recommendBitrate()` 按分辨率给码率
- `remote` 页默认选自适应，并在选中时联动码率（1440P→6000、1080P→4000、720P→2500）
- 被控端收到 `billdDeskStartRemoteResult` 后，先把参数写进本地 ref 再 `handleRTC()`
- `remoteDesk.newWebRtc` 解开注释，把 `maxBitrate/maxFramerate/resolutionRatio` 真正传给 `WebRTCClass`
  （`setMaxBitrate` 会在 `connectionState === 'connected'` 时生效）

修复后 Windows 侧连接参数已变为 `resolutionRatio=1440&maxBitrate=6000`。
**被控端（Mac）必须更新到同一提交并重新 `build:local` 重启**，码率才会真正应用到发送端；
只更新 Windows 侧无效，因为推流发生在被控端。

### 若更新后仍然糊

按顺序看：

1. 被控端 `video` 的实际采集分辨率（Mac 上 `desktopCapturer` 给的源），确认屏幕本身够大
2. 被控端 `setMaxBitrate` 是否成功（控制台有「设置最大码率成功/失败」）
3. 主控端 `video.videoWidth/videoHeight` 是否随码率提升（仍为 1440×810 说明发送端没升级）
4. 最后再考虑改 `videoFullBox`，让它「只缩小不放大」（需要同时调整居中和黑边，属布局改动）



## 十二、用两端实际画面数据定位模糊

配置里的分辨率、码率、帧率只是目标值，必须分别检查采集、编码发送、解码接收和最终显示。

- Mac 被控端：连接中的设备列表下方显示“实时画面”，包含采集和发送两行。
- Windows 主控端：远控窗口打开“连接详情”，查看新增的“实时画面”表与显示缩放信息。
- 两端都需要运行包含本节修复的本地构建。每秒刷新；首个差分样本显示 `—`，不伪造 0。

| 阶段 | 数据来源 | 核对内容 |
| --- | --- | --- |
| 采集 | getStats 的 media-source；探针补充 track.getSettings | 采集像素宽高、实际帧率 |
| 发送 | outbound-rtp | 编码帧宽高、编码帧率、实际发送 kbps、codec、qualityLimitationReason |
| 接收 | inbound-rtp | 解码帧宽高、解码帧率、实际接收 kbps、codec、累计丢帧 |
| 显示 | videoWidth/videoHeight、DOM 渲染尺寸、devicePixelRatio | 物理显示像素及放大倍数；大于 1 代表放大 |

实际码率为 `Δbytes × 8 / Δtimestamp(ms)`，单位 kbps；实际编码/解码帧率为 `Δframes × 1000 / Δtimestamp(ms)`。这是视频 RTP 统计，不包含完整 VPN/网络协议开销。静态桌面实际码率低于设置上限是正常现象，不能单凭“不到 6000”判断故障。

### 本机查到的额外问题及修正

- 一次实际会话请求 1440P，但采集和发送都是 1920×1080、约 30fps，qualityLimitationReason 为 none，不能直接归因于拥塞降档。
- 独立探针复现：仅传 height 约束时，浏览器会重新选择宽度，甚至改变画面比例。改为记住轨道原始采集宽高，同时约束目标宽高并保持比例；不把低分辨率源强行放大。
- 真实横屏验证：2560×1440 → 1280×720 → 2560×1440。竖屏验证：900×1440 → 450×720 → 900×1440，比例均保持。
- 修复 setMaxBitrate 将内部 kbps 错存成 bps 的问题，防止重连后重复乘 1000；无视频发送器或编码参数时及时返回，避免 Promise 挂起。
- 桌面发送器设置 maintain-resolution，优先保持文字分辨率；它不保证任意带宽下都清晰，仍需结合实际统计验证。

判定顺序：源采集不足先查捕获与约束；源足够但发送缩小看发送参数、带宽/CPU 限制；发送足够但接收解码/帧率异常看接收统计、丢包与解码；两端分辨率一致但显示放大再处理缩放布局。仅比较两端码率差值不足以证明网络丢包，需要结合丢包及时间窗口。

自动验证：`node --test test/videoStats.test.cjs`。统计字段定义参考 [W3C WebRTC Stats](https://w3c.github.io/webrtc-stats/)。

## 十三、首次采集就被限制在 1080P（2026-10-29）

`5d5ccf5` 之后的一次实际会话仍出现：请求 1440P、6000 kbps，但采集与编码均为 1920×1080，限制原因为 none。仅修正后续 applyConstraints 不够：如果最初取得的轨道已经是 1080P，后续保护“源尺寸”的逻辑会保留这个上限。

修复：主进程明确选择主屏，按 display.size × scaleFactor 获取物理像素宽高，通过屏幕采集 IPC 返回；renderer 首次 getUserMedia 同时传入 min/maxWidth 和 min/maxHeight，先取得原始尺寸，再根据远控设置缩小。失败时返回可见错误，避免把不存在的 stream 当作成功。

验证结果：

- 实际 Mac 会话的采集和 outbound-rtp 均已变为 **2560×1440**；某些后续样本为 **41–49fps**（该会话请求 60fps），限制原因为 none。帧率会随静态画面和负载变化，不应把它写成恒定保证。
- 独立的本机接收器通过正常鉴权与 WebRTC 信令连接生产 Mac 客户端，实际解码 **2560×1440**、framesDecoded 持续增长，测试样本 packetsLost 为 0。这个接收器位于 Mac 本机，不代表已经读取了 Windows 的接收统计。
- Windows 提供的截图仅显示旧信息区：1920×1080、帧率 0、延迟/丢包 -1，没有“实时画面”表。0/-1 不足以判定解码或网络故障，应先核对窗口实际加载的构建和截图是否来自旧会话。
- 若 Windows 更新后仍看不到新表，保留本地改动，拉取本分支最新提交，执行 npm run build:local，退出托盘及所有旧远控窗口再启动。新窗口“连接详情”应明确出现“实时画面（每秒更新…）”，再对照接收尺寸与物理显示放大倍数。

发送端 1080P 上限已在实际会话和独立接收器中验证解除；Windows 最终视觉清晰度和显示缩放仍以最新窗口的统计及用户反馈为准。
